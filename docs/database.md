# Database schema v1

smalog stores its canonical data in one relational database selected by the
`database.url` scheme in the [configuration](configuration.md#database).
SQLite and PostgreSQL implement the same logical schema.

smalog schema v1 is identified by these rows in `schema_metadata`:

```text
schema_version         1
created_by             smalog
implementation_version 1
```

This identity is unrelated to SBFspot's `Config.SchemaVersion = 1`. The two
version numbers describe incompatible schemas. A smalog-v1 database has no
SBFspot tables or views, and must not be used by `SBFspotUploadDaemon`, legacy
Grafana SQL, or other SBFspot database consumers. See the
[migration guide](migration-sbfspot.md) to move an existing database.

CSV files retain their documented SBFspot-compatible file layout and MQTT
retains its `MQTT_Data`-compatible payload; neither is a claim of database
compatibility. Both are generated by smalog from the canonical model.

## Backends and initialization

### SQLite

```toml
[database]
url = "sqlite:///var/lib/smalog/smalog.db"
```

The file is created automatically when it does not exist. smalog uses WAL
mode, a two-second busy timeout, foreign keys, and one connection. SQLite
identity columns are `INTEGER PRIMARY KEY AUTOINCREMENT`; all logical 64-bit
integer values use SQLite `INTEGER`.

### PostgreSQL

```toml
[database]
url = "postgres://smalog:${SMALOG_DB_PASSWORD}@db:5432/smalog"
```

The role and empty database must already exist. Identity columns use
`BIGINT GENERATED BY DEFAULT AS IDENTITY`; calendar dates use `DATE`.
`postgresql://` is accepted as an alias.

Startup initializes only an empty database. It accepts an existing supported
smalog-v1 database and applies pending ordered migrations. It rejects a
newer smalog schema, an SBFspot-shaped database, and any unrelated non-empty
database. Schema migrations are owned and embedded by `smalog-storage` from
`src/crates/smalog-storage/migrations/{sqlite,postgres}`.

## Types, units, nulls, and UTF-8

- `measured_at`, `occurred_at`, and every other `*_at` integer are signed
  64-bit Unix epoch seconds in UTC.
- `yield_date` and `statistics_date` are local calendar dates. SQLite stores
  checked ISO-8601 `TEXT` (`YYYY-MM-DD`); PostgreSQL stores `DATE`.
- `*_w` is watts, `*_wh` watt-hours, `*_mv` millivolts, `*_ma`
  milliamperes, `*_mhz` millihertz, `*_s` seconds, `*_permille` thousandths,
  and `*_millicelsius` thousandths of a degree Celsius.
- Energy and time counters use logical 64-bit integers. Instantaneous
  electrical readings and protocol status codes use logical 32-bit integers.
- Zero is a measured value. Missing data is `NULL`, an absent optional child
  row, or an empty MPPT collection.
- MPPT tracker numbers are 1 through 255. Tracker zero is invalid; identifiers
  may be sparse.
- Protocol status fields store numeric codes. Localization happens at the
  API/output boundary.

All canonical text is Unicode encoded as UTF-8. PostgreSQL requires both
server and client encoding `UTF8`. SQLite text columns must have the `TEXT`
storage class; byte blobs are rejected. Canonical writes reject embedded NUL,
and migration transcodes known legacy ISO-8859-1 bytes without replacement
characters.

## Core tables

### Identity and live measurements

| Table | Key and relationships | Contents |
|---|---|---|
| `schema_metadata` | PK `key` | Schema/component version strings. |
| `inverters` | PK `inverter_id`; unique `serial_number` | Stable identity, configured/reported names, model, firmware, transport, SUSy ID, first/last seen. Serial is constrained to unsigned 32-bit range; transport is `ethernet`, `bluetooth`, or `NULL`. |
| `inverter_measurements` | PK `measurement_id`; unique `(inverter_id, measured_at)`; inverter delete restricted | One poll: three AC phases, grid frequency/import/export, energy/time counters, numeric statuses, temperature and Bluetooth signal. |
| `mppt_measurements` | PK `(measurement_id, tracker_number)`; parent delete cascades | Zero to 255 observed MPPT children with DC power/current/voltage. |
| `battery_measurements` | PK/FK `measurement_id`; parent delete cascades | Optional one-to-one state of charge, voltage, current and temperature. |

`inverters` never duplicates a latest measurement. The latest state is the
newest indexed `inverter_measurements` row. A poll writes the identity, parent,
all observed MPPT children, and optional battery child atomically.

### Archive, rollups, events, and consumption

| Table | Key and relationships | Contents |
|---|---|---|
| `inverter_energy_samples` | PK `(inverter_id, measured_at)`; inverter delete restricted | Raw archive cumulative energy and instantaneous power. |
| `inverter_daily_yields` | PK `(inverter_id, yield_date)`; inverter delete restricted | Authoritative daily and cumulative energy, completeness flag, update time. |
| `inverter_events` | PK `(inverter_id, device_event_id)`; inverter delete restricted | Event time/code and canonical UTF-8 type/category/group/tag/old/new/user text. |
| `site_consumption_measurements` | PK `measured_at` | Site consumption energy and power, when consumption polling is enabled. |

Daily rollups use the configured plant timezone and half-open UTC boundaries
for each local day. `daily_energy_wh` is the accepted end counter minus its
baseline. Counter resets or missing baselines produce missing data, not a
fabricated zero. Historic days can be complete; the current day remains
incomplete and is revisited after local midnight. Week, month, and year API
queries aggregate `inverter_daily_yields`, while sub-day queries use raw
samples.

### Migration bookkeeping

| Table | Key | Contents |
|---|---|---|
| `migration_runs` | PK `migration_run_id` | Source fingerprint/identity/schema/timezone, status, timestamps, counts, error and report metadata. |
| `migration_checkpoints` | PK `(migration_run_id, category)`; run delete cascades | Per-category source key, bounded-batch progress, status and report metadata used by `--resume`. |
| `migration_staged_rows` | PK `(migration_run_id, category, source_key)`; run delete cascades | Bounded idempotent staging records used by migration categories. |

These are internal migrator tables, not compatibility objects.

## Optional tables

Optional components are absent by default and record their own metadata
version when enabled:

| Table | Key/index | Behavior |
|---|---|---|
| `inverter_daily_statistics` | PK `(inverter_id, statistics_date)`; index `(statistics_date, inverter_id)` | Rebuildable cache of peak/mean AC/DC power, actual/expected sample counts, coverage timestamps, completeness, calculation time, and source watermark. Normal production/yield results never depend on it. Enabled by `database.daily_statistics = true` or migration `--daily-statistics`. |
| `pvoutput_exports` | PK `(inverter_id, measured_at)` | Optional imported export state (`exported_at`, `attempts`, `last_error`). Created only by migration with `--pvoutput-state legacy-flag`. smalog provides no PVOutput uploader or writable compatibility adapter. |
| `poll_transmissions` | PK `transmission_id` (autoincrement/identity); indexes `(occurred_at)`, `(outcome, transmission_id DESC)`, `(target, transmission_id DESC)` | One row per inverter exchange: occurred-at (epoch **milliseconds**), collector target, transport, protocol, request kind, SMA command, LRI window, duration, total frames, outcome (`ok`/`empty`/`unsupported`/`failed`), error, detail. Metadata only — never frame payloads. |
| `poll_transmission_devices` | PK `(transmission_id, serial_number)` with `ON DELETE CASCADE`; index `(serial_number, transmission_id DESC)` | One row per serial an exchange addressed or that answered it, with its frame count. |

The canonical schema additionally carries:

| Table | Key/index | Behavior |
|---|---|---|
| `inverter_query_support` | PK `(serial_number, query)` | One row per query an inverter answered "LRI not available" to, with the model it reported and the epoch second of the most recent refusal. The collector skips those queries until the entry ages out of its recheck window (30 days), so a firmware update that adds a value is still noticed. Deleting rows makes the next cycle ask again. |

Dropping the daily-statistics component cannot remove authoritative
measurements or daily yields. The PVOutput option performs a one-time import;
it is not a runtime bridge for `SBFspotUploadDaemon`.

### The transmission ring

The two diagnostics tables are created together, keyed by
`diagnostics_version` in `schema_metadata`, the first time the service starts
with `service.transmission_log_retention_hours` above `0`. Enabling them does
**not** change `SCHEMA_VERSION`: they are additive, and a database whose owner
never enables them is byte-for-byte what it was.

The service's own log is deliberately **not** stored. It lives in a
process-memory ring owned by the application, because a log line is cheap to
emit and expensive to store, and persisting one would put a database write
behind every `tracing` call. See [operations](operations.md#logging).

They behave as a ring, pruned by the service after each batch it writes:

- rows older than `service.*_retention_hours` (48 h by default) are deleted,
  with the age measured against the newest stored row rather than a fresh
  clock reading, so a host whose clock has not been set yet does not delete
  its own history;
- rows beyond `service.*_max_entries` are deleted oldest-first, even inside
  the window;
- both deletes run in bounded chunks, so a large backlog cannot hold one long
  write lock.

Setting the retention to `0` stops recording but **never** drops rows or
tables: deleting stored history stays an explicit action. At the default cap
the tables cost about 20 MB on SQLite and 48 MB on PostgreSQL, indexes
included.

Reads are keyset-paged, never offset-paged:

```sql
SELECT * FROM poll_transmissions
WHERE transmission_id < :cursor          -- omit to start at the newest
ORDER BY transmission_id DESC
LIMIT 100;
```

The cursor is the primary key, which keeps increasing across restarts and
across the constant deletes pruning performs — a recomputed or reused key
would make the dashboard skip or repeat entries. Because the page cost is an
index seek plus its rows, paging to the oldest entry of a two-day window costs
the same as reading the newest page. Every supported filter has an index so
that a filter matching almost nothing does not degrade into a backwards scan;
[`smalog-schema-benchmark`](../src/crates/smalog-schema-benchmark/) measures
each of them at the row cap against a one-second budget and fails the run when
a case regresses.

## Indexes and access paths

The core schema intentionally adds only these secondary indexes:

| Index | Columns | Access path |
|---|---|---|
| `inverter_measurements_inverter_time_uq` | `(inverter_id, measured_at)` unique | Per-inverter latest/range lookup and poll idempotency. |
| `inverter_measurements_time_inverter_idx` | `(measured_at, inverter_id)` | Global time range. |
| `inverter_energy_samples_time_inverter_idx` | `(measured_at, inverter_id)` | Archive time range. |
| `inverter_daily_yields_date_inverter_idx` | `(yield_date, inverter_id)` | Fleet calendar rollups. |
| `inverter_events_inverter_time_idx` | `(inverter_id, occurred_at DESC)` | Recent events per inverter. |

Primary and unique keys supply their own indexes. The optional statistics
component adds `inverter_daily_statistics_date_inverter_idx`. There are no
tracker-only, monthly-rollup, BRIN, or partitioning indexes in schema v1.

## Dynamic MPPT API model

`GET /api/diagnostics` returns the observed trackers for each measurement and
the latest measurement as an array:

```json
{
  "timestamp": 1700000000,
  "serial": 2000123456,
  "mppts": [
    {
      "tracker_number": 1,
      "dc_power_w": 800,
      "dc_current_ma": 2100,
      "dc_voltage_mv": 380000
    },
    {
      "tracker_number": 5,
      "dc_power_w": null,
      "dc_current_ma": 900,
      "dc_voltage_mv": 410000
    }
  ]
}
```

Items are numerically ordered, sparse identifiers are preserved, unavailable
components are `null`, and a measurement with no observed tracker returns
`"mppts": []`. Fixed `pdc1`/`pdc2`/`idc1`/`idc2`/`udc1`/`udc2` API fields no
longer exist. See the complete [HTTP API documentation](ui.md#http-api).

## SBFspot-to-v1 mapping

| SBFspot source | smalog v1 target and conversion |
|---|---|
| `Config.SchemaVersion` | Not copied as schema identity; v1 metadata is created by smalog migrations. |
| `Inverters` identity/name/type/SW version | `inverters` identity columns, separated from measured state. |
| `Inverters` latest state | Newest matching `inverter_measurements`, or a documented synthetic parent if no spot row matches. |
| `SpotData` AC/counters/status/temperature | `inverter_measurements`; volts/amps/temperature are converted to `*_mv`, `*_ma`, and `*_millicelsius`; known status text becomes a numeric code. |
| `SpotData.Pdc1/Idc1/Udc1` | `mppt_measurements` tracker 1; A/V are rounded to mA/mV. |
| `SpotData.Pdc2/Idc2/Udc2` | `mppt_measurements` tracker 2; legacy all-zero ambiguity is reported, not discarded. |
| MPPT LRIs in `SpotDataX` | Dynamic `mppt_measurements`, tracker `Key & 0xff`; generic values take precedence over fixed columns. |
| Battery LRIs in `SpotDataX` | Optional `battery_measurements` child. |
| Grid import/export LRIs in `SpotDataX` | `inverter_measurements.grid_import_power_w` / `grid_export_power_w`. |
| `DayData` | `inverter_energy_samples`. |
| `MonthData` | `inverter_daily_yields`, with timestamp converted to local `yield_date`. |
| Derived legacy daily views | Optional statistics are rebuilt from canonical rows, never copied. |
| `EventData` | `inverter_events`, with canonical UTF-8 text. |
| `Consumption` | `site_consumption_measurements`. |
| `DayData.PVoutput` | Optional one-time `pvoutput_exports` import only with `--pvoutput-state legacy-flag`. |

`NULL` remains missing and zero remains zero. The migrator reports malformed
keys, unknown statuses, transcoded text, and unavoidable legacy ambiguity.

## Canonical query examples

Use bound parameters in applications and Grafana. The examples use
`:serial`, `:from_epoch`, and `:to_epoch` placeholders; substitute the binding
syntax required by the client.

Latest measurement for one inverter:

```sql
SELECT im.*
FROM inverter_measurements AS im
JOIN inverters AS i USING (inverter_id)
WHERE i.serial_number = :serial
ORDER BY im.measured_at DESC
LIMIT 1;
```

Grafana-ready AC power in watts over a half-open epoch range:

```sql
SELECT
  im.measured_at AS time_epoch,
  COALESCE(im.ac_power_l1_w, 0)
    + COALESCE(im.ac_power_l2_w, 0)
    + COALESCE(im.ac_power_l3_w, 0) AS ac_power_w
FROM inverter_measurements AS im
JOIN inverters AS i USING (inverter_id)
WHERE i.serial_number = :serial
  AND im.measured_at >= :from_epoch
  AND im.measured_at < :to_epoch
ORDER BY im.measured_at;
```

Dynamic MPPT series without pivoting tracker numbers:

```sql
SELECT
  im.measured_at AS time_epoch,
  mm.tracker_number,
  mm.dc_power_w
FROM inverter_measurements AS im
JOIN inverters AS i USING (inverter_id)
JOIN mppt_measurements AS mm USING (measurement_id)
WHERE i.serial_number = :serial
  AND im.measured_at >= :from_epoch
  AND im.measured_at < :to_epoch
ORDER BY im.measured_at, mm.tracker_number;
```

Daily energy for week/month/year panels:

```sql
SELECT y.yield_date, y.daily_energy_wh, y.is_complete
FROM inverter_daily_yields AS y
JOIN inverters AS i USING (inverter_id)
WHERE i.serial_number = :serial
  AND y.yield_date >= :from_date
  AND y.yield_date < :to_date
ORDER BY y.yield_date;
```

For the service's chart-ready JSON, prefer
`GET /api/history?range=day|week|month|year&serial=...`; use
`strings=true` with a selected serial for dynamic per-tracker day series.
